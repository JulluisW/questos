## The Vision

**The Daily Quest** (repo: `questos`) is an AI-ready **gamified accountability coach** dressed as a medieval tavern notice board. Adventurers (users) belong to **guilds**, forge **campaigns** (goals), break them into **quests** on a Kanban board, and earn XP when they complete work—turning daily habits into a lightweight RPG loop.

Evolution so far:

1. **Phase 1 — browser prototype:** quests in `localStorage`.
2. **Phase 2 — cloud MVP:** Supabase auth + a per-user `quests` table, all client-side (`useQuests` / `useAuth` hooks).
3. **Phase 2.5 — server-first (current):** Next.js 16 server components + server actions, `@supabase/ssr` cookie sessions gated by `proxy.ts`, a guild/campaign/quest schema with RLS in versioned migrations, and the first **AI coach** feature (campaign → quest decomposition).

## Tech Stack

| Layer | Technology | Role |
|--------|------------|------|
| Framework | **Next.js 16** (App Router, Turbopack) | Server components for data loading, server actions for mutations, `proxy.ts` for session gating |

## Project layout

Application code lives under `src/` (config, `public/` and `supabase/` stay at the root). The code is organized **by feature**; `app/` only does routing.

```
src/
├── app/                        # routing only: pages, layouts, globals.css
│   ├── (auth)/                 # /login, /signup
│   └── (dashboard)/            # /board, /board/[campaignId], /board/[campaignId]/timeline, /dashboard, /records
├── features/
│   ├── auth/                   # actions.ts (login/signup/signout), components/ (forms)
│   ├── campaigns/              # actions.ts (createCampaignAction), components/ (Forge Campaign dialog)
│   ├── quests/                 # actions.ts, constants.ts, drag.ts, components/ (board, column, card)
│   ├── ai-coach/               # actions.ts, models.ts, schemas.ts, components/ (decomposer dialog)
│   └── timeline/               # queries.ts, build.ts (pure model), components/ (campaign timeline)
├── components/
│   ├── ui/                     # shared primitives (SubmitButton; shadcn target)
│   └── layout/                 # app shell: AppSidebar, AppHeader
├── lib/
│   ├── supabase/               # client.ts (browser), server.ts (RSC/actions), proxy.ts (session refresh)
│   └── utils.ts                # cn()
├── types/
│   ├── database.types.ts       # generated by Supabase CLI — do not edit by hand
│   └── index.ts                # single source of domain types (Quest, Campaign, QuestStatus, …)
└── proxy.ts                    # Next 16 proxy (formerly middleware) → lib/supabase/proxy.ts
supabase/
├── migrations/                 # schema tables, security functions, RLS policies
└── seed.sql
```

**Conventions**

- `app/` pages stay thin: fetch data with `@/lib/supabase/server`, render components from `@/features/*`.
- Features do not import from each other; anything shared moves to `components/`, `lib/` or `types/`.
- Server-only modules (`lib/supabase/server.ts`, `features/ai-coach/models.ts`) import `server-only` so they can never be bundled into client code.
- File names are kebab-case; import via the `@/*` → `src/*` alias.
- Domain types come from `@/types`, never redefined locally.

## Application State & Data Flow

```mermaid
flowchart TB
  subgraph edge [Next.js proxy]
    Proxy[src/proxy.ts → updateSession]
  end
  subgraph server [Server]
    Pages[app/ server components]
    Actions[features/*/actions.ts]
    SBS[(lib/supabase/server)]
    AI[ai-coach: generateObject + Zod]
  end
  subgraph client [Browser]
    Board[QuestBoard + dnd-kit]
    Dialogs[Forge Campaign / AI Decomposer dialogs]
  end
  subgraph supa [Supabase]
    DB[(guilds, campaigns, quests + RLS)]
  end

  Proxy -->|no user → /login, user on auth page → /board| Pages
  Pages --> SBS --> DB
  Pages --> Board
  Board -->|updateQuestStatusAction| Actions
  Dialogs -->|createCampaignAction / generateCampaignQuestsAction| Actions
  Actions --> SBS
  Actions --> AI
```

1. **Every request** passes through `src/proxy.ts`, which refreshes the Supabase cookie session and redirects unauthenticated users to `/login` (and authenticated users away from `/login`/`/signup` to `/board`).
2. **`/board`** lists campaigns server-side; **Forge Campaign** calls `createCampaignAction`, which resolves the user's guild via `guild_members`, inserts a campaign and redirects to `/board/[campaignId]`.
3. **`/board/[campaignId]`** loads the campaign's quests server-side and hands them to the client `QuestBoard`.
4. **Dragging** a card updates local state and calls `updateQuestStatusAction`.
5. **AI decomposition:** `generateCampaignQuestsAction` asks the model for a `CampaignDecompositionSchema` object, bulk-inserts the quests, and `revalidatePath`s the board.
6. **Status history:** every insert or status change on `quests` is logged by a DB trigger into `quest_status_events` — no app code writes history.

### Campaign timeline (`/board/[campaignId]/timeline`)

**Reference date:** the timeline is plotted on `quest_status_events.changed_at` — the moment a card actually moved — not on `created_at`/`completed_at` alone, which cannot show when work started, time spent waiting vs. working, or cards moved backwards/reopened.

- `features/timeline/queries.ts` (server) loads the campaign, its quests, events and the names of the people involved. If the events table is missing it falls back to `historySource: 'derived'` (history rebuilt from quest timestamps) and the UI says so.
- `features/timeline/build.ts` (pure) turns events into per-quest **segments** (one per stage visit), per-quest metrics (lead time = posted→done, cycle time = first started→done, moves, reopens, time per stage), per-day **cumulative flow** + move counts, and the summary KPIs.
- `components/campaign-timeline.tsx` renders on the client only (dates use the viewer's timezone): KPI tiles → zoom/sort/status filters → one horizontally-scrolling canvas where the flow chart, daily move strip and quest lanes share a single date axis. Hovering a day highlights that column across every lane; hovering a lane segment shows a detail card (stage, entered/left, time in stage, moved by, quest stats). Both hover cards use one Base UI tooltip with detached triggers.
- Backfilled history is flagged `is_inferred` and drawn dashed / labelled "Estimated".

### Legacy (Phase 1–2)

The client-side `useQuests`/`useAuth` hooks, `AuthForm`, `KanbanBoard`, `lib/quests/storage.ts` and `TavernBoard` are gone. `STORAGE_KEY` in `features/quests/constants.ts` is a leftover from the localStorage prototype.

## Gamification Engine

Constants in [`src/features/quests/constants.ts`](src/features/quests/constants.ts): `XP_PER_QUEST = 50`, `XP_PER_MILESTONE = 250`. The DB carries `quests.xp_reward` and `profiles.total_xp`.

**Current state:** XP is **not awarded** in the server-first rewrite yet. The scroll card shows a hard-coded `+100 XP` / `+40 XP`, which disagrees with the constants. The Phase 2 rule (award once when a quest first enters `completed`, `level = floor(xp / 100) + 1`) is the intended behavior to restore—ideally server-side, writing `profiles.total_xp`.

## Database Schema

Versioned in `supabase/migrations/`:

| Migration | Contents |
|-----------|----------|
| `…01_schema_tables.sql` | `profiles`, `guilds`, `guild_members`, `campaigns`, `quests`; enums `guild_role`, `quest_status`, `campaign_status`, `quest_priorities` |
| `…02_security_functions.sql` | `SECURITY DEFINER` helpers used by policies (avoid RLS recursion, Postgres 42P17) |
| `…03_rls_policies.sql` | Row Level Security policies (guild-membership based) |
| `20261104000001_quest_status_events.sql` | Append-only `quest_status_events` log, `on_quest_status_change` trigger (SECURITY DEFINER), read-only RLS, backfill of existing quests (`is_inferred = true`) |

Regenerate `src/types/database.types.ts` with the Supabase CLI after any schema change; `src/types/index.ts` derives `Quest`, `Campaign`, etc. from it. Note the generated `quests.status` and `is_milestone` columns are nullable.

## Authentication & Security

- **Session:** `@supabase/ssr` cookies; refreshed in `lib/supabase/proxy.ts` on every matched request.
- **Route gating:** `src/proxy.ts` (Next 16's replacement for `middleware.ts`). UI gating is convenience only.
- **Enforcement:** RLS in Postgres is the security boundary.
- **Mutations:** only via server actions (`'use server'`) using the server client.
- **Secrets:** only the anon key is `NEXT_PUBLIC_*`. AI keys stay server-side (`models.ts` is `server-only`).
